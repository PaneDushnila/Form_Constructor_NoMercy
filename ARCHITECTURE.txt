Архитектура проекта

1. Назначение системы

Сервис позволяет автору создать опрос или форму, настроить вопросы, опубликовать её по ссылке и посмотреть результаты. Респондент проходит опубликованную форму без регистрации. В MVP нет каталога форм, ролей, совместного редактирования, экспорта и ограничения количества прохождений.

2. Общая схема

Система состоит из React-приложения, FastAPI-сервера и базы SQLite. Браузер отправляет JSON-запросы на REST API с префиксом /api/v1. FastAPI принимает запрос, проверяет права и данные, передаёт операцию в сервисный слой и сохраняет результат через SQLAlchemy.

В production frontend и backend работают через один origin. Прокси раздаёт собранный React и направляет запросы /api в FastAPI. В разработке Vite проксирует API-запросы на Uvicorn.

3. Frontend

Frontend написан на TypeScript, React и Vite. Основные экраны:

/forms — список форм автора;
/forms/{formId}/edit — создание и редактирование формы;
/forms/{formId}/results — сводная статистика;
/forms/{formId}/results/{submissionId} — просмотр одной анкеты;
/f/{slug} — публичная форма для респондента.

В frontend есть общий API-клиент, типы запросов и ответов, редактор вопросов, настройка вариантов, проверка полей и компоненты графиков. После публикации форма открывается только для просмотра, а её публичная ссылка может быть скопирована автором.

4. Backend

Backend написан на Python, FastAPI, Pydantic и Uvicorn. Код разделён на следующие части:

api — HTTP-маршруты и коды ответов;
schemas — форматы входных данных, ответов и ошибок;
services — правила создания, сохранения, публикации и обработки анкет;
db — модели SQLAlchemy, подключения и запросы;
migrations — миграции базы данных;
tests — тесты API и бизнес-правил.

Основные маршруты:

POST /api/v1/forms — создать черновик;
GET /api/v1/forms — получить формы текущего автора;
GET /api/v1/forms/{formId} — получить форму для редактирования;
PUT /api/v1/forms/{formId} — полностью сохранить черновик;
POST /api/v1/forms/{formId}/publish — опубликовать форму;
GET /api/v1/public/forms/{slug} — получить опубликованную форму;
POST /api/v1/public/forms/{slug}/submissions — отправить анкету;
GET /api/v1/forms/{formId}/results/summary — получить статистику;
GET /api/v1/forms/{formId}/submissions — получить список анкет;
GET /api/v1/forms/{formId}/submissions/{submissionId} — получить одну анкету.

5. Жизненный цикл формы

После создания форма получает статус draft и revision 1. В черновике можно менять название, описание, вопросы, варианты и их порядок. Сохранение выполняется целиком через PUT-запрос.

При публикации сервер проверяет название формы, наличие вопросов, названия вопросов, варианты выбора и диапазоны оценок. После успешной публикации статус меняется на published и создаётся уникальный slug. Опубликованная структура больше не изменяется, чтобы старые ответы не потеряли исходные подписи вопросов.

Поддерживаются четыре типа вопросов: text, single_choice, multiple_choice и rating. Для rating используется целочисленный диапазон, например от 1 до 5. Вопросы могут быть обязательными или необязательными.

6. Доступ и безопасность

Авторизация автора в MVP выполняется через анонимную сессию. При создании первой формы сервер выдаёт случайный токен в HttpOnly cookie, а в базе хранится только SHA-256-хеш токена. Сессия используется для получения списка форм, редактирования и просмотра результатов.

Респонденту cookie автора не нужна. Публичный API отдаёт только опубликованную форму и не раскрывает данные автора или результаты. Сервер проверяет владельца каждой формы перед выдачей результатов. Потеря cookie означает потерю доступа автора к его формам в рамках MVP.

7. Модель данных

В SQLite используются следующие таблицы:

authors — авторы и хеши сессий;
forms — формы, статус, revision, slug и даты;
questions — вопросы, тип, обязательность и позиция;
question_options — варианты ответа и их порядок;
submissions — отправленные анкеты;
answers — ответы на вопросы;
answer_options — выбранные варианты для вопросов выбора;
submission_idempotency — ключи для защиты от повторной отправки.

Связи идут от автора к формам, от формы к вопросам и анкетам, от вопроса к вариантам, от анкеты к ответам. Форма, вопросы и все ответы сохраняются с внешними ключами и проверками принадлежности одной форме.

8. Обработка анкеты

Перед сохранением сервер загружает опубликованную схему формы и проверяет все ответы: обязательные вопросы должны быть заполнены, текст не должен быть пустым, варианты должны принадлежать нужному вопросу, а оценка должна находиться в заданном диапазоне.

Анкета и все её ответы записываются одной транзакцией. Если проверка не пройдена, в базе не остаётся частичных данных. Для POST-запроса используется Idempotency-Key: повтор того же запроса не создаёт вторую анкету, а другой запрос с тем же ключом получает ошибку конфликта.

9. Результаты

Сервер считает общее число анкет и статистику по каждому вопросу. Для text показывается число заполненных ответов. Для single_choice и multiple_choice показывается количество выборов каждого варианта, включая варианты с нулевым результатом. Для rating рассчитываются среднее значение и распределение по всему диапазону.

Frontend отображает сводку, графики, список отправленных анкет и полный текст отдельной анкеты. При отсутствии ответов структура статистики сохраняется, а числовые значения показываются как нули; среднее для рейтинга в этом случае равно null.

10. Проверка качества

Нужны миграции Alembic, тесты FastAPI через TestClient, проверка Python-кода Ruff, проверка типов TypeScript и production-сборка Vite. Основной сквозной сценарий: создать черновик, сохранить вопросы, опубликовать форму, открыть публичную ссылку, отправить анкету и увидеть обновлённые результаты.
